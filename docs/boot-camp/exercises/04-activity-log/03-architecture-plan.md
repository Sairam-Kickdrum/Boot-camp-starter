## Approach Summary

Add a `booking_events` table (append-only) and a `BookingEventRepository` with only two methods: `insert` and `listForBooking`. Inject `BookingEventRepository` into `BookingService` via constructor — the same pattern used for `BookingRepository`. Add synchronous event writes inside the three `BookingService` methods that mutate bookings (`bookRoom`, `cancelBooking`, `modifyDates`). Add a `GET /bookings/:id/events` route that enforces ownership and returns events in chronological order. Add a `BookingDetailPage` at `/bookings/:id` that fetches and renders the event timeline, and add a "View details" link on each row in `BookingsPage`.

---

## Interaction Model

Read-only timeline. A user navigates from My Bookings → Booking Detail. The detail page fetches `/api/bookings/:id/events` on mount and renders the event list chronologically (oldest first). Event writes happen inside `BookingService` methods, synchronously, immediately after each DB mutation succeeds.

## Alternatives Considered

**1. Store events as a JSONB array column on the `bookings` row instead of a separate table**

Appending a new event entry to a JSONB array on the existing `bookings` row — no new table required.

Rejected because:
- Querying individual events or filtering by `event_type` requires Postgres JSONB path operators, which are harder to write and impossible to index efficiently.
- The array grows unboundedly on the booking row, making every booking read carry the full history even when history is not needed.
- An append-only table with indexed `booking_id` and `created_at` columns is the canonical pattern for immutable event data. It scales predictably and can be queried like any relation.

**2. Async event bus / message queue**

Publish a domain event to an in-process bus (or an external queue) and have a subscriber write the event row asynchronously.

Rejected because:
- It introduces infrastructure complexity (an event bus or queue) that has no place in a teaching exercise focused on three-layer architecture and JSONB patterns.
- Async event writes risk silent failures — if the write never completes, the log is silently incomplete. Synchronous writes make failures surface immediately inside the service method.
- Exercise 05 (Email Notifications) explicitly teaches fire-and-forget async patterns. Making event writes synchronous in Exercise 04 creates a deliberate, teachable contrast between the two approaches.

## Cross-Service Data Flows

### Event write (happens inside BookingService)

```
BookingService.bookRoom() / cancelBooking() / modifyDates()
  → [existing mutation via BookingRepository]
  → bookingEventRepo.insert({ bookingId, eventType, metadata })
  ← returns void (or the inserted row — either is acceptable)
```

The event write fires synchronously, immediately after the DB mutation succeeds. If `insert()` throws, the error propagates up through the service method — there is no silent failure path.

### Event read (GET /bookings/:id/events)

```
Browser (BookingDetailPage)
  → GET /api/bookings/:id/events          (via getBookingEvents() in lib/api/booking-events.ts)
  → Fastify route: booking-events.ts
  → ownership check: service.getById(id)  — rethrows NotFoundError as ForbiddenError
  → BookingEventRepository.listForBooking(id)   — ASC created_at
  ← returns { events: BookingEvent[] }
  ← BookingDetailPage renders event list
```

Auth: `session` cookie → `requireAuth` preHandler verifies Cognito AccessToken via JWKS → attaches `request.sessionUser`.

## Schema: booking_events Table

```typescript
// db/schema/index.ts additions

export const bookingEventTypeEnum = pgEnum("booking_event_type", [
  "booking_created",
  "booking_cancelled",
  "dates_modified",
]);

export const bookingEvents = pgTable("booking_events", {
  id: uuid("id").primaryKey().defaultRandom(),
  bookingId: uuid("booking_id")
    .notNull()
    .references(() => bookings.id),
  eventType: bookingEventTypeEnum("event_type").notNull(),
  metadata: jsonb("metadata").notNull(),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
});
```

Note: `jsonb` must be imported from `drizzle-orm/pg-core` alongside the existing imports.

## Infrastructure Changes

**New table: `booking_events`**

Steps to create the Drizzle migration:

1. Add the `bookingEventTypeEnum` and `bookingEvents` definitions to `db/schema/index.ts` (see Schema section above).
2. Run `npm run db:generate` from the repo root — Drizzle Kit compares the current schema to the last migration snapshot and generates a new `.sql` file in `db/migrations/`.
3. Verify the generated SQL creates the enum, the table, and the FK constraint. It should look approximately like:
   ```sql
   CREATE TYPE "public"."booking_event_type" AS ENUM('booking_created', 'booking_cancelled', 'dates_modified');
   CREATE TABLE "booking_events" (
     "id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
     "booking_id" uuid NOT NULL,
     "event_type" "booking_event_type" NOT NULL,
     "metadata" jsonb NOT NULL,
     "created_at" timestamp with time zone DEFAULT now() NOT NULL
   );
   ALTER TABLE "booking_events"
     ADD CONSTRAINT "booking_events_booking_id_bookings_id_fk"
     FOREIGN KEY ("booking_id") REFERENCES "public"."bookings"("id")
     ON DELETE no action ON UPDATE no action;
   ```
4. Run `npm run db:migrate` (or `./scripts/db-reset.sh`) to apply it to your local database.

No other infrastructure changes. No new environment variables. No external services.

## Frontend Approach

### BookingDetailPage (`apps/web/src/routes/BookingDetailPage.tsx`)

- **Route param:** `id` from `useParams()` — the booking UUID.
- **Data fetch:** `getBookingEvents(id)` on mount via `useEffect`. Three states: loading, error, data.
- **Rendering:** A chronological list of event cards. Each card shows:
  - A human-readable label for `event_type`: `booking_created` → "Booking created", `booking_cancelled` → "Booking cancelled", `dates_modified` → "Dates modified".
  - The formatted `created_at` timestamp.
  - Relevant metadata fields displayed inline (e.g., for `dates_modified`, show old and new dates).
- **Empty state:** If the events array is empty, show a fallback message ("No events yet.").
- **data-testid requirements:** `booking-detail-page`, `event-list`, `event-item`, `event-type-label`, `event-timestamp` — required by the exercise Playwright test.

### BookingsPage changes

- Each booking row gains a "View details" link: `<Link to={`/bookings/${booking.id}`}>View details</Link>` (React Router `Link`).
- **data-testid:** `view-details-link` — required by the Playwright test.
